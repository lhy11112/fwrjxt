# 技术指标不合理之处分析

> 分析对象：仓库内 `HSimC2一体化指控平台.txt`（与本地 `技术指标.docx` 内容一致的技术指标条文）  
> 说明：本环境未能直接读取 `E:\bhfmfwxt\技术指标.docx`，以下按仓库中同名指标文本进行分析。

---

## 一、总体问题（先看这三条）

1. **软硬件责任边界混乱**：探测距离、探测概率、拦截成功率等本质是传感器/效应器硬件能力，却写成软件集成测试验收指标。
2. **指标可测性差**：大量百分比指标未定义样本、场景、真值来源、统计口径，无法客观验收。
3. **指标互相打架**：同一系统既要求“系统延迟 ≤0.5s、威胁评估 ≤2s”，又允许“界面命令 1–3s、查询 3–5s、GIS 刷新 ≤5s”，实时性叙事自相矛盾。

---

## 二、分项不合理点

### 1. 探测距离 ≥6km、探测概率 ≥90%

| 问题 | 说明 |
|------|------|
| 硬件绑定 | 6km/90% 取决于雷达功率、天线、RCS、频段、天气、地形遮挡，软件无法单独保证 |
| 条件缺失 | 未规定目标类型/RCS、高度、速度、背景杂波、传感器配置、昼夜/气象 |
| 验收主体错位 | 写在“软件集成测试环境”下，易变成无法兑现或只能用仿真注数“刷指标” |

**建议**：改为“在甲方给定传感器型号与标定场景下，软件融合后航迹可用率/融合延迟达到××”；硬件指标单独由设备厂家保证。

---

### 2. 总体目标识别率 ≥95%

| 问题 | 说明 |
|------|------|
| 口径不清 | 未区分机型识别 / 敌我识别 / 有无无人机检测；未给混淆矩阵与类别定义 |
| 缺虚警约束 | 只提识别率、不提虚警率(FAR)/漏警率，极易用“宁可乱报”刷高识别率 |
| 样本不均 | “商用 + 特殊侦察型”混算总体 95%，少数难样本可被多数简单样本掩盖 |
| 模态不明 | RF / 雷达 / 光电哪一路达标算数？融合后还是单传感器？ |

**建议**：分模态、分机型给出 Precision/Recall/F1，并单列 FAR；明确测试集构成与置信度。

---

### 3. 一次性探测并识别 ≥30 架，其中非大疆 ≥20 架

| 问题 | 说明 |
|------|------|
| “探测”与“识别”混用 | 同时跟踪 30 与同时正确识别 30 难度差一个数量级 |
| 场景极端 | 饱和攻击下密集关联（JPDA/MHT）本身是开放难题，作为硬验收过高 |
| 真值难获 | “非大疆 ≥20”需可靠机型真值；外场很难同时布置/标定 20 架非大疆目标 |
| 与识别率叠加 | 30 目标 × 95% 识别，实际要求接近“高密度下几乎全对”，更苛刻 |

**建议**：拆成“同时稳定跟踪批次数”和“机型识别准确率”两条；非大疆比例用实验室回放数据集验收。

---

### 4. 威胁等级评估准确率 ≥90%，端到端 ≤2s

| 问题 | 说明 |
|------|------|
| 意图无客观真值 | 侦察/攻击/诱饵等意图在真实对抗中往往无法事后严格标注，90% 准确率难成立 |
| 时间链不完整 | “从侦测到威胁评估”是否含传感器处理、网络传输、融合、模型推理？边界不清 |
| 与 UI 延迟冲突 | 下文界面命令允许 1–3s，与端到端 2s 叠加后指挥闭环可能超标 |
| 权重可人工改 | 支持指挥员改权重后，准确率如何统计？人工介入是否计入？ |

**建议**：改为“规则+模型分级一致性/专家标注集上的 Kappa”；时延拆成感知时延、融合时延、评估时延分项计量。

---

### 5. 单目标轨迹生成 ≤0.01s（10ms）

| 问题 | 说明 |
|------|------|
| 数量级不合理 | 带 DEM 地形、动力学约束的 RRT*/Hybrid A* 很难稳定 ≤10ms，除非预计算/热启动/极度简化 |
| 与多目标 3s 割裂 | 单目标 10ms、多目标 3s，缺少复杂度模型和降级策略说明 |
| 易诱导造假 | 验收时可能只测空路径或查表，失去指标意义 |

**建议**：改为 P95 时延（如单目标 ≤50–100ms，多目标 ≤1–3s），并规定地图分辨率、约束集合与是否允许热启动。

---

### 6. 路径可行性 ≥98%、轨迹规划成功率 ≥98%、冲突消解成功率 ≥98%

| 问题 | 说明 |
|------|------|
| 指标重复 | 三条高度同源，堆叠百分比制造“很严”的观感，实际验收口径重叠 |
| 定义缺失 | “可行性”指仿真无碰、动力学可达，还是实飞成功？分母是什么？ |
| 与拦截成功率重叠 | 规划成功 ≠ 拦截成功，但条文未区分因果链 |

**建议**：保留一条“规划输出通过可行性校验的比例”，冲突消解单独用“冲突残留率/消解迭代次数”描述。

---

### 7. 拦截成功率 ≥90%（抗干扰）

| 问题 | 说明 |
|------|------|
| 超出软件职责 | 依赖干扰功率、天线指向、频谱占用、无人机抗干扰能力、法规可用手段 |
| “抗干扰鲁棒性”空泛 | 未定义干扰类型、干信比、对抗机型 |
| 验收不可控 | 软件方无法在集成测试中独立兑现动能/射频拦截效果 |

**建议**：软件验收改为“决策正确率/指令下发成功率/闭环时延”；拦截成功率作为系统联试指标，前提条件写清效应器与场景。

---

### 8. 策略模型更新周期 ≤1 小时（热更新）

| 问题 | 说明 |
|------|------|
| 混淆能力与频度 | “支持热更新”是能力；“≤1 小时更新一次”像运维节奏，并非算法性能指标 |
| 缺少安全门槛 | 未提灰度、回滚、校验失败阻断，1 小时热更新本身有风险 |

**建议**：改为“支持不停机加载，单次热更新生效时延 ≤×分钟，并具备校验与回滚”。

---

### 9. 同时规划 ≥10 架拦截无人机

| 问题 | 说明 |
|------|------|
| 装备前提不明 | 实际反制资源可能是若干干扰器/诱骗站，未必有 10 架拦截无人机 |
| 与任务形态不符 | 若主战法是射频干扰/GNSS 诱骗，强调 10 机协同轨迹规划可能方向偏移 |

**建议**：按真实效应器清单改写为“同时调度 ≥N 个效应器任务”，N 与编制一致。

---

### 10. 可视化与交互类指标自相矛盾

| 指标 | 不合理点 |
|------|----------|
| 无线电处理 ≥100 条/秒 | 对频谱侦测偏保守；若含 IQ/宽频扫描则单位“条”定义不清 |
| 系统延迟 ≤0.5s | 与硬杀伤/快速机动场景可能仍偏松；又与 UI 1–5s 矛盾 |
| GIS 首次加载 ≤20s | 对指挥系统过松，且与“实时态势”定位不符 |
| GIS 刷新 ≤5s | 目标若高速运动，5s 刷新会导致态势严重滞后 |
| 一般命令 1–3s / 查询 3–5s | 与系统延迟 0.5s、威胁评估 2s 叙事冲突 |
| 任务 ≥5000 / 存储 ≥10 万 | 容量型指标，与反无作战效能弱相关，且无并发、保留周期、检索条件 |

## 三、结构性缺陷（条文写法层面）

1. **缺基准场景**：无标准测试剧本（单机侦察、多机饱和、山地遮挡、强电磁对抗等）。
2. **缺统计方法**：无样本量、置信区间、P95/P99，只有点估计阈值。
3. **缺负面指标**：几乎不提虚警、误拦、误伤民用航空/己方平台风险。
4. **★项过多且同质**：大量星标都是“××率 ≥90%/98%”，区分度差，难以指导优先级。
5. **研究型表述混入验收**：如“智能某场景”“群体智能”等偏课题表述，不适合作为工程硬指标。

---

## 四、建议的指标重构原则

1. **先分界面**：传感器指标 / 融合软件指标 / 决策软件指标 / 效应器指标 / 人机界面指标，分别归属。
2. **先定场景**：每个百分比绑定具体测试场景与数据集。
3. **时延用分位**：统一用 P95/P99，避免“平均 ≤”。
4. **成对约束**：识别率必须搭配虚警率；规划成功率必须搭配平均耗时与失败降级策略。
5. **删并重复**：98% 系三条合并；容量类指标降为非功能性需求附录。

---

## 五、结论

当前技术指标的主要不合理不在“数字略高”本身，而在：

- 把**硬件能力**写成**软件验收**；
- 把**难以标注的认知问题**（意图/威胁）写成精确准确率；
- 用**重复的高百分比**和**互相冲突的时延**制造看似严格、实则不可测的验收条款。

若不修订，集成测试阶段极易出现：仿真刷数通过、外场无法复现，或甲乙双方对口径长期争议。
